## 项目背景

设备管理平台已有查询、诊断和控制能力，运维人员需要通过自然语言使用这些能力。Agent 要理解问题、选择工具并继续排查，同时遵守现有用户权限，回答来自实际平台和设备结果。

独立设计并实现 Vera，覆盖对话接入、Agent 编排、MCP 工具契约、身份权限、上下文、异步操作核对与独立部署。

## 架构思路

Vera 作为独立服务负责语言理解与工具编排，Core 持有业务数据、权限、设备任务和审计。模型使用平台提供的工具目录，工具执行回到业务服务，设备结果通过真实回执确认。Web 和 Agent 复用同一套平台能力。

这一划分让 Agent 可以独立更新提示词与编排逻辑，设备控制和数据规则仍由 Core 统一维护。模型服务、业务权限和设备执行各有明确边界。

## 架构设计与实现

- 接入 Lark 对话，将用户关联到设备管理平台账号，管理会话与持久化上下文。
- 使用 Google ADK 编排 Gemini 与 MCP 工具，按当前用户能力发现查询、诊断和控制入口。
- 在每次工具执行时重新检查账号状态与 RBAC，将写操作参数与当前用户的明确请求关联。
- 对异步设备操作关联同一设备的 action，读取或等待实际响应，区分已受理、执行中、完成和失败。
- 对设备计数等可直接计算的事实使用服务端结果，诊断结论保留工具来源与错误信息。
- 为 Vera 与 Core 建立内部调用契约、组件发布与回滚流程，保留操作审计和验证记录。

## 关键实现

设备在线只说明连接状态，服务是否正常、存储是否可用、录制是否成功需要查询对应事实。Vera 根据工具返回的信息回答，缺失状态保留为未知，不能由模型补全。

一次路径失败后，Agent 可以根据工具目录继续选择可用的诊断入口。设备操作受理后继续核对结果，避免把“命令已发送”直接报告为执行成功。

工具列表与执行权限都来自设备管理平台，账号停用或权限变化会在下一次调用时生效。对话上下文用于理解连续问题，实际授权与设备状态重新从平台读取。

## 交付与验证

Vera 已作为设备平台的独立服务交付。验证覆盖身份与权限、工具选择、设备事实摘要、诊断闭环和发布健康，检查实际工具结果及副作用，逐项记录设备操作的验收范围。
